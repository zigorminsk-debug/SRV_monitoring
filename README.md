# SRV Monitoring

Самостоятельно размещаемая система мониторинга инфраструктуры для Windows Server: веб-панель, сервер опроса, SQLite-хранилище, коллекторы VMware/Redfish/IPMI, общий JSON-коннектор резервного копирования и исходящие Windows-агенты.

> В репозитории реализована рабочая базовая версия, а не только макет интерфейса. Для прямого подключения к Vinchin нужно указать endpoint и структуру ответа, документированные именно для вашей редакции/версии Vinchin. Коннектор не подставляет выдуманные URL и не изменяет конфигурацию бэкапов.

## Что входит

- **Веб-дашборд на HTML/CSS/JavaScript**: общее состояние, критические устройства, предупреждения, история CPU/RAM, журнал тревог, реестр устройств. Виджеты можно скрывать/показывать; персональные настройки вида хранятся в браузере.
- **Сервер опроса**: периодический асинхронный сбор с регулируемым интервалом (15 секунд — 24 часа), параллельные подключения, ручной опрос и история запусков.
- **VMware ESXi/vCenter** (`pyVmomi`, read-only): состояние подключения ESXi, CPU/RAM, аппаратные сенсоры vSphere Health System, состояние физических SCSI-дисков, доступность и свободное место datastore. Пороги datastore настраиваются в форме источника.
- **Redfish**: системное/шасси-состояние BMC, диски, датчики температуры, вентиляторы и питание по стандартному DMTF Redfish API. Поддерживаются контроллеры, совместимые с Redfish (например, iDRAC/iLO/XClarity).
- **IPMI**: чтение сенсоров и последних записей SEL с помощью `ipmitool`; пароль передаётся утилите через переменную окружения, а не аргумент командной строки.
- **Резервное копирование / Vinchin**: read-only JSON API-коннектор. В интерфейсе задаются URL, Basic/Bearer auth, JSON-пути к заданиям/имени/статусу/времени, значения успеха/ошибки и ожидаемая периодичность бэкапа. Если API вашей версии недоступен, состояние можно передавать через локальный файл или пользовательскую проверку Windows-агента.
- **Удалённый Windows-агент**: сам инициирует HTTPS-запрос к серверу, поэтому на удалённом узле не нужен входящий публичный порт. Передаются hostname, CPU, память, свободное место на дисках, выбранные Windows-сервисы, события Error/Critical журналов System/Application, а также пользовательские проверки/статус бэкапа.
- **Тревоги**: сохраняются в SQLite, повторные события агрегируются, при восстановлении проверки закрываются, событие можно принять в работу.
- **Защита**: сессионный вход администратора, ограничение попыток входа, хеширование токенов агентов, шифрование конфигураций источников ключом Fernet, TLS-проверка включена по умолчанию.

## Архитектура

Модель намеренно похожа на архитектуру Zabbix/других систем наблюдаемости, но упрощена для установки на один Windows-сервер:

```text
ESXi/vCenter ─┐
BMC Redfish ──┼─ HTTPS/API или IPMI ─> Collector/Scheduler ─> SQLite ─> HTML Dashboard
BMC IPMI ────┤                            │                    │
Backup JSON ─┘                            └─ пороговые проверки ┴─> Alerts

Удалённые Windows-клиенты ── исходящий HTTPS + индивидуальный токен ──> /api/ingest/{agent_id}
```

Роли компонентов:

1. **Коллекторы** знают протокол источника и переводят результат в общую модель `status / checks / metrics / devices`.
2. **Планировщик** запускает проверки по общему интервалу; сетевые сбои фиксируются отдельно и эскалируются после повторного неуспешного опроса.
3. **Хранилище** сохраняет последние состояния, историю опросов, измерения и события.
4. **Правила** применяют пороги, объединяют повторяющиеся события и отмечают восстановление.
5. **Агенты** работают по push-модели: только исходящее соединение с центральным сервером.
6. **Веб-интерфейс** показывает состояние и позволяет настраивать источники/интервал, не открывая доступ к секретам источников.

Отличие от крупной установки Zabbix: сейчас это один сервер и один SQLite-файл, без отдельных proxy-серверов, HA-кластера, RBAC, оповещений по e-mail/SMS и шаблонов автодискавери. Для небольшого/среднего контура это упрощает запуск; для большого числа узлов следует перейти на PostgreSQL и вынести poller/notification workers отдельно.

## Запуск на Windows Server

Требуется Windows Server 2019+ и Python 3.11 x64. Откройте PowerShell в каталоге проекта:

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\start_windows.ps1
```

Скрипт создаст `.venv`, установит `requirements.txt`, создаст `.env` из `.env.example` и запустит сервер. В примере включён обязательный HTTPS: сначала настройте reverse proxy/сертификат или задайте `SSL_CERTFILE` и `SSL_KEYFILE`; без TLS панель вернёт `426 HTTPS required`. Для локальной изолированной проверки можно временно поставить `REQUIRE_HTTPS=false`, но не оставляйте это значение на публичном интерфейсе. На первом запуске, если `ADMIN_PASSWORD` пуст, случайный пароль будет сохранён в `data/initial-admin-password.txt` и показан в консоли. Войдите под пользователем `admin`, задайте собственный длинный пароль в `.env` и ограничьте ACL для этого файла.

По умолчанию панель слушает `0.0.0.0:8765`. Для постоянного запуска как задача Windows (из повышенного PowerShell):

```powershell
.\scripts\install_server_task.ps1
Start-ScheduledTask -TaskName 'SRV Monitoring Server'
```

Журнал запуска задачи доступен в Task Scheduler. Для ручной остановки завершите процесс PowerShell/uvicorn или остановите задачу.

### Публикация на сервере с белым IP

Не публикуйте административную панель по обычному HTTP. Рекомендуемая схема:

1. Привяжите доменное имя к белому IP и установите TLS-сертификат.
2. Поставьте IIS с URL Rewrite + Application Request Routing либо другой reverse proxy, который завершает HTTPS и передаёт запросы на локальный `http://127.0.0.1:8765`.
3. В `.env` задайте `APP_HOST=127.0.0.1`, `SECURE_COOKIES=true`, `REQUIRE_HTTPS=true`, `PUBLIC_BASE_URL=https://ваш-домен` и `TRUSTED_HOSTS=ваш-домен`; reverse proxy должен передавать `X-Forwarded-Proto: https`. Запускаемый скрипт включает Uvicorn proxy headers и по умолчанию доверяет forwarded-заголовкам только от localhost.
4. На внешнем firewall откройте только TCP/443 (и ограничьте список администраторских IP, если возможно). Порт 8765 оставьте доступным только локально/reverse proxy.
5. Для удалённых агентов задайте `server_url` с публичным HTTPS-доменом. Оставьте `verify_tls: true`.

Альтернативно можно задать в `.env` `SSL_CERTFILE` и `SSL_KEYFILE` и завершать TLS непосредственно в Uvicorn. Не забывайте ограничить доступ firewall-ом. Если у сервера только IP без домена, заранее продумайте сертификат, которому доверяют браузеры и агенты.

У серверного узла должен быть сетевой маршрут до ESXi/vCenter, BMC и backup API — обычно через VPN/site-to-site VPN, а не через публикацию этих интерфейсов в Интернет. Создайте для VMware/BMC/Backup отдельные read-only учётные записи с минимально необходимыми правами.

## Готовые setup.exe через GitHub Actions

Workflow `.github/workflows/windows-installers.yml` собирает self-contained Windows executable и оборачивает их в установщики Inno Setup. Он запускается при push в Arena-ветку и вручную через **Actions → Build Windows installers → Run workflow**. После успешной сборки скачайте артефакт **SRV-Monitoring-Windows-Installers** на странице запуска workflow (**Actions → Build Windows installers → последний run → Artifacts**); срок хранения — 30 дней. Внутри будут файлы:

- `SRV-Monitoring-Server-Setup.exe` — сервер без требования устанавливать Python на целевую машину;
- `SRV-Monitoring-Agent-Setup.exe` — удалённый агент без требования устанавливать Python.

Установщик сервера попросит публичный HTTPS URL, порт, допустимые Host и PEM certificate/private key. Он скопирует TLS-ключи и настройки в `%ProgramData%\SRV Monitoring`, добавит задачу Windows Scheduler от `SYSTEM` и откроет входящий TCP-порт выбранного HTTPS-порта в Windows Firewall. Ограничьте этот порт внешним firewall до доверенных адресов, если это возможно. Bootstrap-пароль будет создан при первом старте в `%ProgramData%\SRV Monitoring\data\initial-admin-password.txt`.

Установщик агента запросит HTTPS URL сервера, Agent ID и одноразовый token. Сначала создайте агент в веб-панели, затем вставьте эти значения в установщик. Конфигурация сохраняется с ограниченными ACL в `%ProgramData%\SRV Monitoring Agent\agent.json`; задача агента запускается при загрузке Windows. При удалении приложения конфигурация, токен и база данных намеренно сохраняются.

## Подключение источников

Войдите в панель → **Добавить источник**. Пароли и токены не возвращаются в API после сохранения; при редактировании секрет оставьте пустым, чтобы не менять его.

### VMware

- Укажите IP/FQDN ESXi или vCenter, порт (обычно 443), пользователя и пароль.
- Для vCenter собирается доступная инвентаризация ESXi-хостов и datastore; прямое подключение к ESXi также поддерживается.
- Проверка сертификата включена. Если в тестовой сети временно отключить её, это будет видно как предупреждение.
- Проверка состояния физического диска зависит от контроллера, драйвера и того, что vSphere публикует через API. Для контроля аппаратных сенсоров/дисков рекомендуется дополнить VMware-опрос Redfish/IPMI.

### Redfish

Укажите базовый URL BMC, например `https://10.20.0.12`, и read-only пользователя. Коллектор использует ссылки из Redfish root, Systems, Chassis, Storage, Thermal и Power. BMC без полного набора этих ресурсов может вернуть меньше показателей; недоступный отдельный ресурс будет показан как предупреждение.

### IPMI

Установите `ipmitool` на Windows Server и укажите путь к `ipmitool.exe`, если он не находится в `PATH`. Коллектор использует IPMI over LAN (`lanplus`) и команды `sensor list`/`sel elist`. Утилита должна иметь сетевой доступ к UDP/623 на BMC.

### Vinchin / другое резервное копирование

В типе источника **JSON API (Vinchin)** задайте endpoint чтения списка заданий и поля ответа. Поддерживаются dotted JSON paths (`data.jobs`, `jobs.0.status`) и стандартные значения `success/succeeded/completed/ok` и `failed/error/aborted`.

Структура и доступность API зависят от версии и настроек Vinchin. Поэтому URL и JSON-пути нужно сверить с документацией вашей установки или проверить на read-only endpoint; приложение не пытается автоматически входить в веб-интерфейс и не выдумывает внутренние API-маршруты. Скриптовый пример `examples/vinchin-api-adapter.ps1` читает документированный HTTPS JSON endpoint и выводит формат, подходящий удалённому агенту.

Если прямого API нет:

- настройте локальный скрипт/экспортёр, который пишет `checks` и `metrics` в JSON-файл, и задайте путь в агенте как `backup_status_file`; или
- добавьте его в `external_checks` агента. Команда задаётся **локально** в `agent.json`, не приходит с сервера.

Образец формата: `examples/backup-status.example.json`. Ошибки заданий и отсутствие ожидаемого запуска поднимают предупреждение/критическое событие.

## Подключение удалённого Windows-агента

1. Откройте **Устройства → Подключить удалённый агент** и задайте имя. Панель покажет `agent_id`, секретный токен и заготовку `agent.json` один раз.
2. Установите Python 3.11 x64 на удалённом Windows-узле; скопируйте каталог `agent/` (или его скрипт/requirements) в защищённую папку.
3. Сохраните заготовку как `agent.json`, установите зависимости и запустите:

   ```powershell
   .\run_agent.ps1
   ```

4. Для запуска при загрузке системы из повышенного PowerShell выполните `agent\install_agent_task.ps1`. Задайте ACL на каталог агента и `agent.json`: в них находится bearer token.
5. При первой отправке агент появится в реестре. Агент обращается к серверу по исходящему HTTPS, ему не нужен входящий публичный порт.

Настройки по умолчанию: heartbeat каждые 60 секунд, проверки дисков/CPU/RAM и Windows event logs. Список контролируемых служб, интервал и пользовательские проверки задаются в `agent.json`. Для работы с журналами событий могут потребоваться соответствующие локальные права.

В примере `examples/vinchin-api.json.example` хранится локальная конфигурация read-only API для `examples/vinchin-api-adapter.ps1`. Скопируйте её в защищённое место на узле агента, исправьте URL/пути под свою версию Vinchin и ограничьте ACL. Затем добавьте в `agent.json` локальную пользовательскую проверку (укажите свой фактический путь к `.ps1`):

```json
{
  "name": "Vinchin Backup API",
  "command": "powershell.exe",
  "args": ["-NoProfile", "-NonInteractive", "-ExecutionPolicy", "Bypass", "-File", "C:\\ProgramData\\SRV-Monitoring\\vinchin-api-adapter.ps1"],
  "timeout_seconds": 45
}
```

Поместите этот объект внутрь массива `external_checks`. Адаптер выводит JSON со статусом `ok`, `warning` или `critical`; агент отправит его в центральную панель. Не храните реальные пароли в Git.

## Конфигурация и данные

- `.env` — локальные параметры сервера; файл игнорируется Git.
- `data/monitoring.sqlite3` — устройства, последние значения, история и тревоги.
- `data/encryption.key` — ключ шифрования паролей источников. **Сделайте защищённую резервную копию вместе с БД.** При потере или замене ключа сохранённые credentials расшифровать нельзя.
- `data/session.key` — ключ подписи пользовательской сессии.
- `data/initial-admin-password.txt` — только bootstrap-пароль, если `ADMIN_PASSWORD` не задан.

При переносе сервера перенесите БД и исходный `encryption.key` в закрытый каталог с ограниченными ACL. Не включайте `data/`, `.env`, `agent.json`, токены и реальные backup-конфиги в публичный Git/backup без шифрования.

Интервал центрального опроса регулируется на странице **Настройки**. Для снижения нагрузки можно увеличить его; вендорские BMC обычно не требуют частого опроса. Интервал агента задаётся независимо в `agent.json`. Планировщик ежедневно чистит измерения старше 90 дней, журналы опросов старше 30 дней (и оставляет не более 1000 запусков на источник), а разрешённые события хранит 180 дней.

## Разработка и тесты

```bash
python -m venv .venv
# Windows: .venv\Scripts\Activate.ps1
# Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
pip install pytest
python -m pytest -q
# Только локальная изолированная разработка; для production настройте HTTPS.
# Windows PowerShell:
$env:REQUIRE_HTTPS = 'false'
python -m uvicorn srv_monitoring.app:app --host 0.0.0.0 --port 8765
# Linux/macOS: REQUIRE_HTTPS=false python -m uvicorn srv_monitoring.app:app --host 0.0.0.0 --port 8765
```

Для первого входа локально прочитайте `data/initial-admin-password.txt`, если собственный `ADMIN_PASSWORD` не задан.

## Ограничения текущей версии

- Один локальный администратор; нет multi-user/RBAC.
- Уведомления отображаются в панели; SMTP/Telegram/SMS/webhook-рассылки ещё не реализованы.
- SQLite хорошо подходит для небольшого контура, но не является HA-хранилищем для тысяч узлов и высокой частоты опроса.
- Нет автоматического discovery сети, корреляции топологии или выполнения удалённых команд сервером.
- Для VMware аппаратные диски/датчики доступны не на каждом сочетании ESXi, RAID-контроллера, драйвера и firmware; при необходимости проверяйте данные BMC.
- Vinchin-интеграция намеренно generic: до ввода в эксплуатацию проверьте endpoint, поля статуса, формат времени и read-only учётную запись на реальном ответе API.
